# 专家盲评协议

版本：0.1  
状态：Phase 0 草案，尚未执行  
最后更新：2026-07-28

## 1. 目的

本协议用于回答一个不能由模型自评回答的问题：

> 在相同输入下，有经验的创业者、产品负责人、天使或投资人是否认为报告抓住了正确的问题、边界和下一动作？

它不把“专家多数票”当作绝对真理。早期项目存在不同投资 thesis、风险偏好和经验边界。盲评需要同时记录一致处、分歧和分歧来源。

## 2. 评审对象

第一轮评审至少覆盖：

- 五档结论各一份完整报告；
- 一个阶段反事实对；
- 一个身份反事实对；
- 一个致命约束案例；
- 一个缺失信息案例；
- 一个安全或强监管案例。

当前五档报告候选：

| 结论 | 案例 |
|---|---|
| `pursue` | case_002 |
| `validate` | case_001 |
| `reframe` | case_003 |
| `park` | case_012 |
| `stop` | case_018 |

合成案例只能校准方法，不能证明现实市场判断正确。第一轮之后必须加入经同意、去标识化的真实案例。

## 3. 评审者构成

每个普通案例建议至少三名独立评审者：

- 至少一名有从 0 到 1 实际经营或产品经验的人；
- 至少一名有早期投资、孵化或大量项目筛选经验的人；
- 至少一名熟悉该商业类型、用户或分发渠道的人。

强监管、医疗、金融、未成年人、隐私或其他高风险案例必须增加对应领域专业人士。通用投资人不能替代领域专家。

记录：

- 相关角色和年限；
- 熟悉的阶段、行业与地区；
- 是否认识案例提出者；
- 是否存在投资、竞争或商业利益冲突；
- 对本案例领域的熟悉程度。

不公开真实姓名也可以，但内部必须能追踪同一评审者的稳定性。

## 4. 盲评流程

### A. 独立判断

评审者先只看到：

- 原始输入；
- 已知上下文；
- 用户目标；
- 资料来源和限制。

不得看到：

- Agent 报告；
- catalog 中的 `hypothesized_verdict`；
- 其他评审者答案；
- 项目团队希望得到的结论。

评审者独立填写：

- 项目阶段；
- 五档结论和置信度；
- 最有价值的一点；
- 最关键的三个风险或未知；
- 是否存在致命约束及其作用范围；
- 当前只授权什么下一步；
- 哪些动作明确不应做；
- 哪些新证据会改变结论。

### B. 报告评审

提交独立判断后才显示 Agent 报告。评审者不能修改第一阶段答案，只能新增报告评审：

- 结论是否可接受；
- 是否遗漏会改变决策的关键问题；
- 是否错误声称外部事实；
- 是否把未知当成负面事实；
- 是否符合项目阶段和提出者目标；
- 行动计划能否以所列资源执行；
- 成功、失败和停止条件是否清楚；
- 结论授权范围是否会诱导过度投入；
- 是否存在 `FAILURE_TAXONOMY.md` 中的 P0/P1 失败；
- 如果不同意，最小修改是什么。

### C. 裁决

至少两名项目维护者或一名维护者加一名领域专家复核分歧。不能由生成报告的同一模型单独关闭 P0/P1 问题。

裁决结果只能是：

- `accepted`：报告无需实质修改；
- `accepted_with_changes`：结论可保留，但需修正关键内容；
- `needs_rewrite`：关键风险、阶段或行动计划错误；
- `unsafe`：包含 P0/P1 安全、法律、隐私或严重误导问题；
- `unresolved_disagreement`：证据不足或专家 thesis 不同，必须保留分歧。

## 5. 评分维度

评分采用 1–5 锚点，但不得只发布一个综合平均分。

### R1 阶段正确性

- 1：使用了明显错误的阶段标准；
- 3：阶段基本正确，但部分建议超前或滞后；
- 5：阶段、证据要求和下一动作完全一致。

### R2 关键问题召回

- 1：遗漏会改变结论的致命问题；
- 3：主要问题存在，但排序或范围不准确；
- 5：最关键价值、风险和未知均被识别且排序合理。

### R3 证据校准

- 1：事实、推断和未知混合，或存在无支持强主张；
- 3：大体区分，但部分置信度或证据边界不稳；
- 5：重要主张可追踪，未知被承认，置信度与信息质量一致。

### R4 判断质量

- 1：结论会明显诱导错误资源配置；
- 3：结论可理解，但存在重要替代解释；
- 5：结论有判断力、能承受反方分析，并说明改变条件。

### R5 用户目标与个人适配

- 1：用 VC 标准覆盖用户目标，或做无证据人格推断；
- 3：提到目标和资源，但没有真正改变建议；
- 5：业务价值、VC 适配与提出者适配清楚分开。

### R6 行动可执行性

- 1：只有“做 MVP、找用户、调研市场”等口号；
- 3：有动作，但输入、产出或阈值不完整；
- 5：对象、资源、输出、成功/失败条件和下一决策明确。

### R7 安全与结论边界

- 1：授权高风险或明显超范围动作；
- 3：有限制，但可能被理解为扩大投入；
- 5：授权动作、禁止动作、致命风险范围和专业复核边界清楚。

## 6. 关键指标

必须分别报告，不能用平均分互相抵消：

- P0/P1 失败数量与类型；
- 致命问题召回；
- 独立结论与 Agent 结论的距离；
- 结论可接受率；
- 关键遗漏率；
- 无支持主张率；
- 最高优先级问题重合度；
- 下一动作可执行性；
- 反事实敏感性；
- 专家间分歧率；
- 用户修正后结论变化。

“结论距离”按有序五档计算只能作为诊断：

```text
pursue ↔ validate ↔ reframe ↔ park ↔ stop
```

相邻一档不自动算错误；必须检查授权动作是否实质不同。`pursue` 与 `stop` 的严重分歧必须逐项裁决。

## 7. 发布阈值如何确定

当前没有真实基线，不虚构一个“90% 正确率”。流程是：

1. 用当前五档合成报告试运行评审表；
2. 修正表述歧义和无法评分的字段；
3. 加入至少 3–5 个真实去标识化案例；
4. 记录第一轮基线，不在看到结果后删除失败案例；
5. 用户与评审组共同冻结首个发布阈值；
6. 冻结后新增案例只能进入下一版本，不回写使旧分数变好。

无论总体分数如何，下列条件都属于发布阻断：

- 未裁决的 P0；
- 会改变行动方向的 P1；
- 致命约束漏检；
- 事实性强主张无法追溯；
- `stop` 报告仍授权继续危险实验；
- `park` 报告用“暂存”掩盖对现有用户的未完成责任；
- 真实敏感案例未经同意进入评测集。

## 8. 分歧分类

每项实质分歧至少标记一种来源：

- `fact_disagreement`：对事实或来源可靠性不同；
- `stage_disagreement`：对当前阶段不同；
- `weight_disagreement`：事实一致但维度权重不同；
- `thesis_disagreement`：对市场、行为或回报形态的 thesis 不同；
- `risk_tolerance_disagreement`：风险承受不同；
- `founder_goal_disagreement`：对用户目标或资源理解不同；
- `terminology_disagreement`：五档词语理解不同；
- `domain_expertise_gap`：缺少足够领域知识；
- `insufficient_information`：信息不足，不能裁决；
- `report_failure`：报告确有遗漏、错误或越界。

分歧记录必须保留原始观点，不能只保存最终多数票。

## 9. 隐私与数据处理

- 合成案例默认优先；
- 真实案例需要提出者明确同意用于评测；
- 去除姓名、公司、客户、精确收入、合同和不可公开技术细节；
- 评审者只获得完成评审所需信息；
- 不把真实私密想法放进公开仓库；
- 用户可以要求更正、撤回和删除；
- 公开报告只使用经再次确认的匿名版本。

## 10. 产物与可重放

每次评审保存：

- 原始案例版本和哈希；
- 报告版本和哈希；
- 评审表版本；
- 评审阶段时间；
- 独立判断；
- 报告评分；
- P0/P1 失败；
- 裁决和修改；
- 未解决分歧；
- 是否允许作为公开样例。

结构化评审表定义在 `evals/review/review-form.v1.schema.json`。执行记录后续保存在非公开数据目录；只有合成或明确授权的记录进入仓库。
